# Database Seed Scripts

Seed scripts populate data after the schema migrations have run. They are idempotent (`ON CONFLICT …`), so they are safe to run more than once. Run them with `scripts/run-seeds.sh` (`pnpm db:seed`).

## Reference data vs test fixtures

| File | Kind | Loaded in |
| --- | --- | --- |
| `001_seed_authorities.sql` | Reference: 10 UAE authorities (DMCC, IFZA, DED, RAKEZ, ADGM, DIFC, SHAMS, DAFZA, JAFZA, ADCCI) | every environment |
| `002_seed_categories.sql` | Reference: template categories | every environment |
| `003_seed_test_tenants_users.sql` | Fixture: 3 test tenants, 7 test users with the **published password** `Test123!@#`, including a `system_admin` | development / test only |
| `004_seed_templates.sql` | Fixture: sample templates, `created_by` = test users | development / test only |
| `005_seed_test_documents.sql` | Fixture: tenant documents for RLS testing | development / test only |
| `006_seed_features_plans.sql` | Fixture: a snapshot of features and plans that has drifted from the code (e.g. Shield price) | development / test only |
| `007_seed_test_subscriptions.sql` | Fixture: subscriptions for the test tenants | development / test only |
| `008_seed_test_entitlements.sql` | Fixture: add-ons and overrides for the test tenants | development / test only |
| `009_seed_rulesets.sql` | Fixture: 5 demo rulesets, `created_by` = the seeded superadmin | development / test only |
| `010_seed_ruleset_chunks.sql` | Fixture: pre-computed embeddings for 009 (generated by `pnpm db:generate-chunk-seed`) | development / test only |

Data that isn't seeded at all:

- **Features, plans and plan entitlements** are upserted from `apps/api/src/common/constants/plan-entitlements.constant.ts` by `EntitlementSyncService` on every API start.
- **Tenant and platform RBAC** comes from `TenantRbacSyncService` / `PlatformRbacSyncService`, also on startup.
- **Platform admins** are never seeded outside development. Create one with `pnpm admin:grant <email>` (see `docs/DEPLOYMENT.md`), which emails a set-password link.

## How the split is enforced

`run-seeds.sh` loads test fixtures only when:

1. the environment argument is `development` (the default) or `test`, **and**
2. `NODE_ENV` is unset or `development`/`test`. It checks both the value in your shell and any value sourced from `apps/api/.env`.

For `staging`, `production`, or any production-like `NODE_ENV`, it loads the reference seeds only and says which fixtures it skipped. An unknown environment name is rejected.

As a second line of defence, `003_seed_test_tenants_users.sql` refuses to run unless the session has `complytude.allow_fixtures = 'on'`. `run-seeds.sh` sets that (through `PGOPTIONS`) only for fixture files it has decided to load. A stray `psql -f 003_…` fails and creates no accounts. The other fixtures depend on 003's tenants and users.

## Running

```bash
./scripts/run-seeds.sh                 # development: reference + fixtures
./scripts/run-seeds.sh test            # reference + fixtures
./scripts/run-seeds.sh staging         # reference only
./scripts/run-seeds.sh production      # reference only
./scripts/run-seeds.sh staging --list  # print what would run, without touching the database
```

The script loads `apps/api/.env` (or `.env.api` / `.env` / `.env.<environment>`), tests the connection, runs the files in dependency order, and prints table counts. It prints the test credentials only when fixtures were loaded.

Running a fixture by hand needs the flag, for example:

```bash
PGOPTIONS='-c complytude.allow_fixtures=on' psql -U <user> -d <db> -f scripts/seeds/003_seed_test_tenants_users.sql
```

Only do that against a local database.

## Testing RLS Policies

After seeding a development database, you can test Row-Level Security with these queries:

```sql
-- Set context for Tenant 1 Admin
SELECT set_config('app.tenant_id', '11111111-1111-4111-8111-111111111111', false);
SELECT set_config('app.user_id', 'aaaaaaaa-aaaa-4aaa-aaaa-aaaaaaaaaaaa', false);
SELECT set_config('app.role', 'admin', false);

-- Should return 3 documents for Tenant 1
SELECT * FROM public.documents;

-- Change to Tenant 2 context
SELECT set_config('app.tenant_id', '22222222-2222-4222-8222-222222222222', false);
SELECT set_config('app.user_id', 'dddddddd-dddd-4ddd-dddd-dddddddddddd', false);

-- Should return 2 documents for Tenant 2 (different set)
SELECT * FROM public.documents;

-- Global tables should be accessible from any tenant
SELECT * FROM public.authorities;
SELECT * FROM public.categories;
SELECT * FROM public.templates;
```
